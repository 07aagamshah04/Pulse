   with the current one, so accept() rarely has to wait for a brand-new
   handshake to start. that's connection-setup overlap, not the server's
   own work becoming parallel.

what each row means:
  Connect    = time to complete the TCP handshake (Week 1, Part 3) before
               any HTTP bytes are even sent
  Processing = time from request sent to full response received - this is
               basically the server's read+parse+route+write time
  Waiting    = time from request sent to the FIRST response byte received
               (a "time to first byte" style number) - nearly identical to
               Processing here because these responses are so small there's
               no meaningful gap between "first byte" and "last byte"
  Total      = Connect + Processing combined - the whole request/response
               cycle from the client's point of view

what min/mean/sd/median/max mean (statistics, not this project's syscalls):
  min    = fastest single request observed
  mean   = plain average
  sd     = standard deviation - how spread out the numbers are; small sd
           means most requests were close to the mean, not wildly different
  median = the middle value if you sorted every request's time (the 50th
           percentile) - often more representative than mean when a few
           slow outliers skew the average
  max    = slowest single request observed (worst case)

interesting real observation: at -c 1, Connect max = 8ms and Total max =
14ms, even though the MEAN for both is ~0ms. that's a single outlier (out
of 1000 requests, most likely the very first one - cold OS/network-stack
state before anything warmed up) dragging the max way above the typical
case. at -c 10, max Total is only 4ms - a much tighter, more consistent
distribution. this exact pattern shows up again below in the percentile
table.

what this table means: "95% 1" means 95% of all 1000 requests finished in

-c 10: much smoother - 99% at 4ms, 100% (worst case) ALSO 4ms. no big

COMPARISON TO PREDICTIONS

1. latency prediction ("high latency" for the last client under load): DIRECTION
   CORRECT. mean time/request went 0.494ms -> 1.862ms (~3.8x) under concurrency
   10 - a request arriving while another is being served queues behind it,
   same backlog mechanism from week 1's notes. absolute number stays tiny
   because each request is cheap (parse a few dozen bytes, static string,
   write) - queuing behind 9 others only costs ~1.4ms extra.

2. throughput prediction ("flat"): WRONG, and this is the interesting one.
   actual: req/sec MORE than doubled (2023 -> 5372). doesn't contradict
   "server handles one client at a time" once you separate two different
   things:
     - SERVER PROCESSING: genuinely sequential, one at a time, unchanged
     - CONNECTION SETUP (TCP handshake): NOT serialized the same way
   at -c 1: fully serial from client's view - connect -> wait full response
   -> close -> connect again. every handshake waits for the PREVIOUS
   request's entire round trip first.
   at -c 10: ab keeps 10 connections in flight - while server is busy on
   request #1, kernel can already complete handshakes for #2-10 in the
   backlog queue. by the time accept() loops back, a connection is often
   already sitting there ready, instead of server idling for a brand-new
   handshake. server's OWN work never parallelizes - this is connection-
   setup overlap, not request-processing overlap.

3. CPU prediction ("kept in queue till accept"): CONCEPTUALLY CORRECT. a
   connection sitting in the backlog runs none of my code - pure kernel
   bookkeeping, essentially free. NOT YET CONFIRMED NUMERICALLY - still
   need the ps CPU/mem snapshot (stage B step 5) to see the actual %.
